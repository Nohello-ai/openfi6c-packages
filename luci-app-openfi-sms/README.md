# luci-app-openfi-sms

OpenFi 6C 的**短信**：列表、弹窗看全文、发送、（可选）删除。

菜单在 **移动网络 → 短信**（和「模组信息与卡槽」「信号与流量」「AT 终端」并列）。

* **列表整体滚动**（`max-height` + `overflow-y:auto`），页面本身不滚 —— 手机上更好用
* **整行都是点击热区**，点开是**弹窗**（`ui.showModal`），**不跳页面**
* 预览用 CSS 截断（`-webkit-line-clamp:2`），点弹窗看全文
* 布局只用 LuCI 标准 class，不写死颜色，跟随主题

## 为什么单独一个包

* **PDU 编解码是纯计算**，跟「模组信息/切卡」不是一类事，拆开各自演进
* 但它**必须复用 `luci-app-openfi-modem` 的 `/usr/lib/openfi-modem/at.sh`** ——
  那里有**串口互斥锁**。不通同一把锁的话，你在短信页刷新时，
  模组信息页正好也在查，两条 AT 指令会互相插话。
  `LUCI_DEPENDS` 里已经声明了这个依赖。

## 为什么用 ucode 写 PDU

两个包原本都是 `LUCI_PKGARCH:=all`（架构无关）。
PDU 编解码是「十六进制 ↔ 位 ↔ 字节序 ↔ 字符集」的活：
* shell 干这个会难查十倍
* C/Rust 会让包变成架构相关，CI 要配交叉工具链、编译时间变长
* ucode 是解释型的，有位运算 / `sprintf("%02x")` / `chr`/`ord`/`substr`，
  包仍然是 `Architecture: all`

`usr/lib/openfi-sms/pdu.uc` 里标了 **10 个坑**（BCD 半字节交换、GSM7 低位在前、
UDH 的 septet 对齐、TON 在 bit4~6、`int("0xff")` 在 ucode 里返回 0、
时区是 BCD 十进制、**两个地址字段长度单位不一样**、无 UDH 时 payload 从 0 开始…）
—— 这些就是「短信功能」真正的工作量，靠真机抓的 PDU 样本做回归测试。

## 长短信

运营商把长短信拆成多段发（UDH 里带 `ref / 总段数 / 段号`）。
`pdu.uc` 的 `joinConcat()` 按 `(发件人, ref, 总段数)` 归组、按段号排序后拼起来。
**不做这个的话，用户看到的是两条破碎的半截消息。**

实测样本里就有：一条「区域流量使用80%提醒」被拆成 3 段。

## 数据从哪来

**直接读 SIM 卡，不本地存镜像**：SIM 能存 50 条，短信本来就在卡上。
已读/未读用 SIM 自带的状态位（点开时发一次 `AT+CMGR`，副作用就是标记已读）。

只有**发件箱**要本地存（`/etc/openfi-sms/sent.json`），因为发出去的短信
模组不一定保留。

## 接口

| 动作 | 说明 |
| --- | --- |
| `openfi-sms list` | 列 SIM 上所有短信（JSON，长短信已拼好） |
| `openfi-sms mark <idx>` | 标记已读（`AT+CMGR` 的副作用） |
| `openfi-sms delete <idx>` | 从 SIM 删除 |
| `openfi-sms sent` | 本地发件箱 |
| `openfi-sms send <号码> <内容>` | **待实现** |

`send` 需要 PDU **编码**（当前模组是 `+CMGF:0` PDU 模式），而且**会真的发出去**
—— 真机测试要花钱/占额度，所以单独一步做，不草率实现。
